# PR #10 Owner hours regression

The failed `10:00:00` assertion exposed an asynchronous setup refresh race. A preceding staff mutation had reached PostgreSQL, so a database poll could succeed before the browser completed its setup/dashboard refresh. The still-editable old drawer accepted a new hours value. The pending refresh then replaced that input with persisted `09:00`, and the next save submitted the old value. This was a real lost-edit defect, not a reason to change the expected hour.

Setup mutations now lock controls synchronously and keep them locked through the refresh. A status message and aria-busy communicate progress, and duplicate saves are ignored. The new weekly RPC validates all seven days and applies them in one transaction, using the same staff advisory lock as booking validation. Its migration is pending and has only been applied to disposable CI databases. Coordinate that migration before any future frontend release; production has not been changed.

Working hours are SQL `time without time zone` and remain business-local strings. They must not pass through JavaScript Date or UTC conversion. Dated time-off values are different: the existing RPC converts business-local timestamps using the business IANA timezone and rejects nonexistent spring-forward times. London 10:00 is 10:00Z in winter and 09:00Z in summer; neither changes a weekly 10:00 opening time.

The original expected `10:00:00` remains. Browser tests assert both the submitted 10:00 payload and the persisted value, then the refreshed input. Desktop Chromium runs in America/Los_Angeles and touch-enabled mobile WebKit in Asia/Tokyo, while the business is Europe/London. SQL tests independently vary database session timezones across UTC, Los Angeles and Tokyo, verify winter/summer offsets, reject a DST gap, and check that an invalid week rolls back atomically. The local save-lock regression is confirmed to fail when the lock is removed.

The Owner workflow runs all sixteen tests without fail-fast skipping. It exercises actual local GoTrue magic links delivered into Mailpit, signed sessions, refresh, server logout and revoked refresh-token replay; all five industries; appointment/CRM/setup/branding/import/intelligence workflows; two-owner tenant boundaries and staff-role escalation denial. Auth, PostgREST and PostgreSQL are real local services; no hosted user or customer fixture is created. Owner accessibility scans retain all WCAG assertions. Contrast and scroll-region keyboard defects discovered by the suite were repaired.

The recovery drill dumps only the disposable synthetic database, encrypts with AES-256-GCM, verifies decryption and rejection of corruption, restores into a separate database, compares all application/Auth rows and application policies/functions/grants/constraints, and rechecks restored RLS. Grant comparison normalizes only table_catalog because the target database name necessarily differs. An intentional grant change on the disposable target must still be detected and reversed. Dump files and private keys are not uploaded. Hosted production backup and recovery remain a separate operational gate.

Notification integration uses a loopback Resend-contract server with real SQL queue transitions. It checks default-disabled dispatch, 429/backoff/retry, stable idempotency, stale claims, signed webhook events, replay protection, out-of-order delivery/bounce handling, suppression and anonymous denial. This is not actual Resend delivery evidence. Real provider verification requires an approved sender/test recipient and secure credentials; no customer emails or marketing are sent.

GitHub Actions results and artifacts at the exact PR head are the authoritative test outcomes. Do not infer a production release from these checks. No merge or deployment is authorised in this task.
